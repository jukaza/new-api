# Kế hoạch: Đơn giản hóa tính năng Nhóm (Group)

## Nguyên tắc đã thống nhất với user
1. **Tất cả channel tự động phục vụ mọi nhóm** — admin không cần gán group cho channel/model nữa.
2. **Nhập % giảm giá** (10 = giảm 10% so với giá gốc), thay vì hệ số ratio `0.9`.
3. **Xoá sạch group khỏi phía user** — không còn dropdown chọn nhóm trong tạo API key, playground, v.v.
4. **Reset nhóm mặc định chỉ còn `default`** — xoá `vip`/`svip` hardcode, admin tự thêm nhóm giảm giá.

## Cơ chế đơn giản sau khi sửa
- Admin tạo nhóm: **Tên nhóm + % giảm giá**.
- Admin gán user vào nhóm trong form user.
- User thuộc nhóm nào thì **tự động được giảm %** khi dùng API.
- Mọi channel luôn phục vụ mọi nhóm — không cần setup group cho từng channel/model.

## Phase 1 — Backend: Channel phục vụ mọi nhóm

### Mục tiêu
Khi tạo/sửa channel, hệ thống tự sinh abilities cho **tất cả các nhóm hiện có**, không chỉ nhóm trong `channel.Group`. Khi lookup channel, group không còn là ràng buộc.

### File cần sửa
- `model/ability.go:158-198` (`AddAbilities`) và `:206-279` (`UpdateAbilities`)
  - Bỏ split theo `channel.Group`.
  - Lấy danh sách tất cả nhóm từ `ratio_setting.GetGroupRatioCopy()`.
  - Với mỗi model của channel, sinh ability `(group, model, channelId)` cho mọi group.
- `model/channel_cache.go:22-87` (`InitChannelCache`)
  - Với mỗi channel + model, thêm channelId vào **tất cả** group trong `group2model2channels`.
- `model/channel_satisfy.go:8-31` (`IsChannelEnabledForGroupModel`)
  - Trả về true nếu channel enabled cho model, không cần kiểm tra group.
- `model/ability.go:118-156` (`GetChannel` — DB fallback khi tắt memory cache)
  - Bỏ điều kiện `commonGroupCol = ?`, chỉ lọc theo `model` và `enabled`.

### Lưu ý
- Giữ nguyên cột `channels.group` để tránh migration phá dữ liệu, nhưng backend sẽ **bỏ qua** giá trị đó trong routing.
- `Ability` table vẫn giữ cột `group` để không phá schema; dữ liệu sẽ được đồng bộ theo cơ chế mới.

## Phase 2 — Backend: Giảm giá theo nhóm user

### Mục tiêu
- Xoá các nhóm mặc định `vip`/`svip` hardcode.
- Đảm bảo billing lấy nhóm của **user** làm usingGroup (vì token không còn chọn group từ FE).

### File cần sửa
- `setting/ratio_setting/group_ratio.go:12-16`
  - `defaultGroupRatio` chỉ còn `{"default": 1}`.
- `setting/user_usable_group.go:10-13`
  - `userUsableGroups` chỉ còn `{"default": "Nhóm mặc định"}`.
- `setting/auto_group.go:7-9`
  - `autoGroups` mặc định `[]string{"default"}` (hoặc xoá hoàn toàn nếu không còn dùng).
- `common/topup-ratio.go:8-11`
  - `topupGroupRatio` chỉ còn `{"default": 1}`.
- `middleware/auth.go:382-399`
  - Vẫn giữ logic fallback: nếu `token.Group` rỗng thì `usingGroup = userGroup`.
  - Token group selection đã bị xoá ở FE nên thực tế user luôn dùng userGroup.
- `relay/helper/price.go:36-62` và `service/quota.go:108-136`
  - Không cần đổi logic tính ratio, chỉ cần đảm bảo `relayInfo.UsingGroup = user.Group`.
  - `GetGroupRatio` trả về `1` cho nhóm chưa có ratio (an toàn).

### Về % giảm giá
- Backend vẫn lưu **ratio multiplier** (`0.9` = giảm 10%).
- Frontend admin sẽ chuyển đổi: hiển thị và nhập `% giảm`, lưu xuống dưới dạng `ratio = 1 - discount/100`.
- Như vậy hạn chế thay đổi backend, tránh ảnh hưởng relay/billing/usage log.

### Chuyển đổi % giảm ↔ ratio
- Load: `discount = Math.round((1 - ratio) * 100)`.
- Save: `ratio = 1 - discount / 100`.
- Validate: `0 <= discount <= 100`.

## Rủi ro & giảm thiểu
- **Dữ liệu cũ**: Cột `channels.group` và `abilities.group` được giữ, dữ liệu cũ sẽ được đồng bộ lại khi channel được update hoặc khi chạy `FixAbility`.
- **Token group cũ**: Nếu user/tokens cũ có `group != ""`, backend vẫn tôn trọng nếu hợp lệ. FE mới không cho phép tạo/sửa token group.
- **Billing**: Chỉ thay đổi cách nhập ở FE, backend vẫn dùng multiplier nên tính toán quota không đổi.
